# 0005. 중복은 DB 제약으로 막고, 가입된 이메일은 409 로 알린다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0001](0001-email-verification-timing.md)

## 맥락

`userId` 와 `email` 은 각각 유일해야 한다. 두 가지를 정해야 한다.

1. 중복을 무엇으로 막을 것인가 — 조회 후 검사인가, DB 제약인가.
2. 이미 가입된 이메일로 인증을 요청하면 어떻게 응답할 것인가.

2번은 보안과 사용성이 충돌한다. 409 로 명확히 알려주면 사용자는 "이미 가입하셨습니다"를
바로 보지만, 공격자도 **임의의 이메일이 이 서비스에 가입되어 있는지 확인**할 수 있다
(account enumeration).

## 결정

**중복 방지**

- `user.user_id`, `user.email` 에 DB 유니크 제약을 건다. **이것이 유일한 방어선이다.**
- 유스케이스의 `existsBy...` 사전 검사는 유지하되, 역할은 **에러 메시지 품질**로 한정한다.
  이것으로 중복을 막았다고 간주하지 않는다.
- `storage-db` 어댑터가 제약 위반 예외를 잡아 도메인 예외
  (`DuplicateUserIdException` / `DuplicateEmailException`)로 번역한다.

**이메일 존재 노출**

- 이미 가입된 이메일로 인증을 요청하면 **`409 DUPLICATE_EMAIL`** 로 명확히 응답한다.

## 근거

**중복 방지를 DB 제약에 맡기는 이유**

조회 후 검사는 동시 요청을 막지 못한다. 두 요청이 같은 `userId` 로 동시에 들어오면
둘 다 `existsByUserId == false` 를 보고 둘 다 저장으로 넘어간다. 검사와 저장 사이의
간격은 트랜잭션 격리 수준으로도 닫히지 않는다(팬텀에 해당하고, 삽입끼리는 충돌하지 않는다).
유니크 인덱스만이 이 경합에서 정확히 한쪽을 떨어뜨린다.

그렇다고 사전 검사를 없애지는 않는다. 제약 위반은 "어느 컬럼이 충돌했는지"를
드라이버 메시지에서 파싱해야 알 수 있어 신뢰하기 어렵다. 평시에는 사전 검사가
정확한 메시지를 주고, 경합 시에는 제약이 정합성을 지킨다. **역할이 다르다.**

**409 를 택한 이유**

노출을 감수한다. 근거는 이 서비스에서 **감출 수 있는 정보가 아니기 때문**이다.

- 가입 단계(`POST /users`)에서는 `email` 중복을 어차피 알려야 한다. 인증 단계에서만
  가려봐야 한 단계 뒤에서 드러난다. 실질적 보호가 아니라 사용자만 헷갈린다.
- 가리는 구현(성공한 척하고 "이미 가입된 계정입니다" 안내 메일을 대신 발송)은
  프론트 흐름을 복잡하게 만든다. 폼은 인증이 진행 중이라 믿고 폴링을 시작하지만
  영원히 `VERIFIED` 가 되지 않는다.
- 커머스 서비스라 이메일 가입 여부의 민감도가 낮다.

대신 **열거 자체를 비싸게** 만든다. 인증 요청 엔드포인트에 IP·이메일 단위
호출 제한을 건다(별도 작업으로 분리, 아래 참조).

## 결과

**얻는 것**

- 경합 상황에서도 중복 계정이 생기지 않는다.
- JPA/드라이버 예외가 `api` 계층까지 새지 않는다. 어댑터 경계에서 번역된다.
- 사용자는 이미 가입했다는 사실을 첫 단계에서 안다.

**치르는 비용**

- 이메일 가입 여부가 외부에서 확인 가능하다. **의도된 선택이며**, 호출 제한으로 완화한다.
- 어댑터가 드라이버별 제약 위반 예외를 다뤄야 한다. H2 에서 실 DB 로 옮길 때
  이 번역 코드에 대한 테스트가 필요하다.

## 유일성의 정확한 정의

대소문자 차이로 사실상 같은 계정이 둘 생기는 것을 막는다.

- `userId`: 입력은 영문 대소문자와 숫자를 허용하되 **소문자로 정규화해 저장·비교**한다.
  `Alice` 와 `alice` 가 다른 계정이 되면 사용자가 자기 아이디를 헷갈리고,
  시각적으로 유사한 아이디를 사칭에 쓸 수 있다.
- `email`: 전체를 **소문자로 정규화**한다. 로컬 파트는 규격상 대소문자를 구분하지만
  실제로 구분하는 메일 서버는 없다시피 하다.

정규화는 값 객체(`UserId`, `Email`) 생성 시점에 한다. 저장소가 아니라 도메인의 책임이다.

## 후속 작업

- 인증 요청 엔드포인트 호출 제한(IP / 이메일 단위). 이번 범위에 넣지 않는다.
- 탈퇴 회원의 `userId` / `email` 재사용 정책. `WITHDRAWN` 상태를 도입할 때 정한다.
