# 0014. 재고는 상품이 들고, 차감은 조건부 원자 갱신으로만 한다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0005](0005-uniqueness-and-email-enumeration.md), [0008](0008-login-token-strategy.md), [0011](0011-single-sellable-unit.md)

## 맥락

재고를 어디에 두고 어떻게 줄이는가. 실제로 답해야 할 질문은 하나다 —
**초과 판매(oversell)를 무엇이 막는가.**

재고가 1개 남은 상품에 주문이 동시에 둘 들어오는 상황이 기준이다. 이 저장소에는
같은 형태의 경합이 이미 두 번 나왔다. 중복 가입([0005](0005-uniqueness-and-email-enumeration.md))과
리프레시 토큰 재사용([0008](0008-login-token-strategy.md))이다. 둘 다 "읽고 판단하고 쓰는"
사이에 다른 요청이 끼어들어 깨졌다.

## 결정

**재고 위치** — `products.stock_quantity` 컬럼 하나. 재고 이력 테이블을 두지 않는다.

**차감 경로는 하나뿐이다.** 포트에 조건부 원자 갱신을 둔다.

```kotlin
/** 재고가 충분할 때만 줄이고, 줄였는지 알려준다 */
fun decreaseStockIfEnough(id: Long, quantity: Int): Boolean
```

구현은 갱신된 행 수를 그대로 돌려준다.

```sql
UPDATE products
   SET stock_quantity = stock_quantity - :quantity
 WHERE id = :id AND stock_quantity >= :quantity
```

**도메인 모델은 재고를 줄이지 않는다.** `Product` 는 읽고 판정만 한다
(`canFulfill(quantity)`). `decreaseStock` 같은 메서드를 **두지 않는다.**

**품절은 저장하지 않는다.** `stockQuantity == 0` 에서 파생한다.

## 근거

**왜 조회 후 차감이 아닌가**

두 요청이 재고 1을 함께 읽고, 둘 다 "충분하다"고 판단하고, 둘 다 저장한다. 최종 재고는
0 이 되고 상품은 두 번 팔린다. 트랜잭션 격리 수준을 올려도 갱신 손실은 남는다.
[0005](0005-uniqueness-and-email-enumeration.md) 의 결론을 그대로 가져온다 —
**경합은 DB 가 판정한다.**

**왜 비관적 락(`SELECT ... FOR UPDATE`)이 아닌가**

정확하지만 비싸다. 인기 상품 한 행에 주문이 직렬화되고, **주문 트랜잭션이 재고 외의
일(결제 호출 등)을 함께 하면 그 시간만큼 락을 물고 있다.** 락 보유 구간이 외부 호출을
포함하는 순간 대기 시간이 우리 손을 떠난다.

**왜 낙관적 락(`@Version`)이 아닌가**

낙관적 락은 "잃어버린 갱신을 **감지**해서 호출자가 재시도" 하는 도구다. 재고 차감이
필요로 하는 것은 감지가 아니라 **판정의 원자성**이다 — 충분하면 줄이고 아니면 실패,
한 번에. 게다가 경합이 몰리는 인기 상품일수록 재시도가 반복 실패해서, 가장 필요한
곳에서 가장 나쁘게 동작한다.

**왜 도메인에 차감 메서드를 두지 않는가**

두면 반드시 누군가 쓴다. 그리고 **단위 테스트에서는 완벽하게 통과한다** — 단일 스레드로
돌리면 재고는 정확히 맞는다. 문제는 운영에서만, 그것도 트래픽이 몰릴 때만 나타난다.
있으면 안전해 보이는데 안전하지 않은 메서드가 가장 나쁘다. 아예 없애서 잘못 쓸 수
있는 문을 닫는다.

`Product.canFulfill` 은 남긴다. 이것은 차감이 아니라 **표시와 사전 안내**를 위한
판정이고, 실제 방어선이 아니라는 점이 이름에 드러난다.

**왜 재고 이력 테이블이 없는가**

지금 답해야 하는 질문은 "현재 재고가 얼마인가" 하나다. 이력이 필요해지는 시점은
정산과 감사이고, 그때는 주문 도메인이 이미 "무엇이 언제 몇 개 팔렸는가"를 들고 있다.
같은 사실을 두 곳에 적으면 둘이 어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없다.

**왜 품절을 컬럼으로 두지 않는가**

[`EmailVerification`](../core/core-domain/src/main/kotlin/com/example/shopapi/core/domain/verification/EmailVerification.kt)
이 상태를 타임스탬프에서 파생한 것과 같은 이유다. 저장하면 재고 수량과 어긋날 수 있고,
어긋났을 때 어느 쪽이 진실인지 알 방법이 없다. 파생하면 어긋날 수가 없다.

## 결과

**얻는 것**

- 초과 판매가 구조적으로 불가능하다. 락도 재시도도 없다.
- 재고 판정이 SQL 한 문장이라, 주문 트랜잭션이 길어져도 경합 구간이 늘지 않는다.
- `stock_quantity` 에 음수가 들어갈 수 없다. `WHERE` 절이 곧 불변식이다.

**치르는 비용 — 분명히 해 둔다**

- **이번 범위에는 이 포트를 부를 소비자가 없다.** 차감은 주문이 하는 일이고 주문
  도메인이 아직 없다. 구현과 동시성 테스트는 지금 하고, 배선은 주문에서 한다.
- **벌크 `UPDATE` 는 JPA 영속성 컨텍스트를 우회한다.** 같은 트랜잭션에서 차감 이전에
  읽어 둔 엔티티는 **낡은 재고를 들고 있고**, 그 상태로 다른 필드를 저장하면 차감이
  되돌아간다. `@Modifying(clearAutomatically = true, flushAutomatically = true)` 로
  비우거나, 차감 뒤에는 그 엔티티를 다시 쓰지 않는다.
- **복원(`increaseStock`)은 상한 검사를 우회한다.** 원자 덧셈이라
  `StockQuantity` 의 상한을 통과하지 않는다. 취소·환불로 복원되는 수량은 이전에
  차감된 수량이므로 실무상 상한을 넘지 않지만, **불변식이 값 객체가 아니라 호출자에게
  걸려 있다는 뜻**이다.
- 재고가 언제 왜 변했는지 알 수 없다. 감사 요구가 생기면 이력이 필요해진다.

## 재검토 시점

재고 이력·입출고 관리가 요구사항이 될 때, 또는 [0011](0011-single-sellable-unit.md) 을
뒤집어 재고가 변형 단위로 내려갈 때. 후자의 경우 이 결정의 형태는 그대로 유지되고
대상 테이블만 바뀐다.
