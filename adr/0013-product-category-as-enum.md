# 0013. 상품 카테고리는 코드 enum 으로 시작한다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0011](0011-single-sellable-unit.md), [0015](0015-product-list-pagination.md)

## 맥락

상품을 분류할 수단이 필요하다. 목록 조회의 주된 필터가 카테고리이기 때문이다.

두 가지를 정해야 한다.

1. 카테고리를 **테이블**로 둘 것인가 **코드 enum** 으로 둘 것인가.
2. **계층**을 둘 것인가.

전제가 하나 있다. 이번 범위에서 관리자·역할 개념을 배제했으므로,
**카테고리를 운영 중에 추가하거나 이름을 고칠 주체가 없다.**

## 결정

`core-enum` 에 `ProductCategory` enum 을 둔다. **계층 없이 한 단계**다.
DB 에는 `@Enumerated(EnumType.STRING)` 으로 **이름을 저장**한다.

## 근거

**왜 테이블이 아닌가**

관리 주체가 없다. 테이블로 두면 지금 생기는 것은 관리 API 없는 빈 테이블, 그것을 채우는
시드 스크립트, 그리고 조회마다 붙는 조인 하나다. **운영자가 고칠 수 없다는 사실은
그대로인데** 구조만 늘어난다.

enum 은 그 대가로 두 가지를 준다 — 잘못된 카테고리 값이 **컴파일 시점에** 걸리고,
카테고리 목록 API 가 `entries` 하나로 끝난다.

**왜 `ordinal` 이 아니라 이름을 저장하는가**

`ordinal` 을 저장하면 enum 상수의 순서를 바꾸거나 중간에 값을 끼워 넣는 순간
**저장된 모든 숫자의 의미가 통째로 어긋난다.** 코드 한 줄 위치를 옮긴 것이 데이터
손상이 되는데, 컴파일러도 테스트도 알려주지 않는다. 기존 `UserStatus`,
`EmailVerificationStatus` 와 같은 방식을 쓴다.

**왜 계층을 두지 않는가**

계층은 "하위 카테고리를 포함해서 검색" 이라는 요구를 데려오고, 그것은 재귀 쿼리 ·
경로 컬럼(materialized path) · 클로저 테이블 중 하나를 고르라는 **별도의 결정**이다.
카테고리가 스무 개 남짓인 동안 두 단계가 주는 이점보다 그 결정의 비용이 크다.

미루는 비용이 낮다는 점이 중요하다. **API 계약은 `category` 필터 하나로 계층이
생겨도 그대로다.** 계층이 도입되면 바뀌는 것은 서버 쪽 조회 구현이지 클라이언트가
보내는 값이 아니다.

**되돌리는 비용**

이름을 저장하므로 enum → 테이블 전환은 **컬럼 타입을 바꿀 필요가 없다.** 현재 값을
그대로 `categories` 의 코드 컬럼으로 옮기고 FK 를 거는 작업이다.

## 결과

**얻는 것**

- 조회에 조인이 없다. 카테고리 필터가 단일 컬럼 조건이라 복합 인덱스에 그대로 들어간다.
- 잘못된 카테고리를 컴파일러가 막는다.

**치르는 비용**

- **카테고리를 하나 추가하려면 배포해야 한다.** 이것이 이 결정의 핵심 비용이다.
- 노출 순서, 아이콘, 설명 같은 표시용 메타데이터를 enum 프로퍼티로 넣을 수는 있지만
  운영자가 고칠 수 없다.
- 카테고리를 **삭제**할 수 없다. 그 카테고리로 저장된 행이 남아 있으면 `reconstitute` 가
  실패한다. 쓰지 않는 카테고리는 지우지 말고 노출에서만 뺀다.

## 재검토 시점

카테고리 변경 요청이 **분기 1회를 넘길 때**, 또는 카테고리별 배너·정렬처럼 운영이
직접 고쳐야 하는 메타데이터가 생길 때. 둘 중 먼저 오는 쪽.
