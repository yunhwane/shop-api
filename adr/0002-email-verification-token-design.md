# 0002. 인증은 링크 토큰으로 하고 식별자를 둘로 나눈다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0001](0001-email-verification-timing.md)

## 맥락

[0001](0001-email-verification-timing.md) 에서 선인증을 택했다. 인증 수단은 두 갈래다.

- **6자리 숫자 코드**: 사용자가 화면에 입력한다. 흐름이 가입 폼 안에서 닫힌다.
  대신 브루트포스가 가능해 시도 횟수 제한과 짧은 만료가 필수다.
- **링크 토큰(UUID)**: 메일의 링크를 누르면 인증된다. 추측이 사실상 불가능하다.
  대신 **흐름이 폼 밖으로 나갔다 온다.**

링크 토큰을 선인증과 결합하면 두 가지 문제가 동시에 생긴다.

1. **완료 통보 경로가 없다.** 사용자는 링크를 누른 뒤 다른 탭에 있다. 원래 가입 폼은
   인증이 끝났다는 사실을 알 방법이 없다. (코드 방식이었다면 생기지 않았을 문제다.)
2. **인증과 가입이 묶이지 않는다.** "이 이메일은 인증됐다"는 서버 상태만으로 가입을
   허용하면, 피해자가 인증을 마친 직후 제3자가 같은 이메일로 가입을 선점할 수 있다.
   창은 좁지만 실재한다.

## 결정

**링크 토큰**을 쓰되, 식별자를 두 개로 분리한다.

| 식별자 | 보관 주체 | 노출 경로 | 용도 |
|---|---|---|---|
| `verificationId` (UUID) | 가입 폼(클라이언트) | 인증 요청의 응답 본문 | 상태 폴링, 가입 요청에 첨부 |
| `token` (UUID) | 메일 수신함 | 메일 링크의 쿼리스트링 | 클릭 시 `verifiedAt` 마킹 |

- 폼은 `verificationId` 로 상태를 폴링해 가입 버튼을 연다. → 문제 1 해결
- 가입 요청은 `verificationId` 를 반드시 동봉한다. → 문제 2 해결

그리고 **메일 링크는 API 를 직접 가리키지 않고 프론트엔드 페이지를 가리킨다.**

```
메일 링크:  https://{front}/verify?token=xxx
프론트가 호출:  POST /api/v1/email-verifications/confirm { token }
```

## 근거

- 두 식별자를 모두 가진 주체만 가입할 수 있다. `token` 만 가로챈 제3자는
  `verificationId` 가 없어 가입하지 못하고, `verificationId` 를 가진 원래 클라이언트는
  메일함 없이는 인증을 통과하지 못한다. 어느 한쪽만으로는 부족하게 설계했다.
- **메일 링크가 서버 `GET` 을 직접 치면 안 된다.** 다수의 메일 클라이언트와 보안 게이트웨이가
  링크를 미리 가져간다(prefetch). 사용자가 누르기도 전에 인증이 완료되어 버린다.
  프론트 페이지를 한 번 경유시키면 실제 브라우저에서 발생한 `POST` 만 인증으로 인정된다.
  부작용 있는 요청이 `GET` 이 아니게 된다는 점도 덤이다.
- `verificationId` 와 `token` 을 하나로 합치면, 클라이언트가 보관하는 값이 곧 인증 열쇠가 된다.
  로그·리퍼러·브라우저 히스토리 어디로든 샐 수 있는 값에 인증 권한을 주지 않는다.

## 결과

**얻는 것**

- 인증을 시작한 클라이언트만 그 인증으로 가입할 수 있다.
- 메일 프리페치로 인한 오인증이 없다.

**치르는 비용**

- 클라이언트가 폴링해야 한다. 실시간성이 필요해지면 SSE 나 WebSocket 으로 바꿔야 한다.
  지금 규모에서는 과하다고 보고 폴링으로 시작한다.
- 프론트엔드에 `/verify` 페이지가 필요하다. API 만으로 인증이 완결되지 않는다.
- `EmailVerification` 이 컬럼을 두 개(그리고 유니크 인덱스를 두 개) 갖는다.

## 세부 규칙

- 만료: 발급 후 **30분**.
- **`consumedAt` 을 둔다.** 가입에 사용된 인증은 소비 처리해 재사용을 막는다.
  없으면 인증 한 번으로 계정을 여러 개 만들 수 있다.
- 같은 이메일로 인증을 재요청하면 기존의 미완료 인증을 무효화하고 새로 발급한다.
- **가입 요청 본문에 `email` 을 받지 않는다.** 이메일은 서버가 `verificationId` 로
  조회한 인증 레코드에서 꺼낸다. 바디로 받으면 A 를 인증하고 B 로 가입하는 경로가 열린다.

## 재검토 시점

모바일 앱을 붙이면 링크 방식의 앱 복귀(딥링크)가 번거롭다. 그때 6자리 코드 방식을
병행할지 판단한다. 식별자 분리 구조 자체는 코드 방식에도 그대로 쓸 수 있다.
