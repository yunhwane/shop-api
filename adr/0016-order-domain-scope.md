# 0016. 주문은 결제·배송 없이 PLACED/CANCELLED 로 시작하고, 소유권 검사는 404 로 감춘다

- 상태: 수락됨
- 날짜: 2026-09-02
- 관련: [0005](0005-uniqueness-and-email-enumeration.md), [0011](0011-single-sellable-unit.md), [0014](0014-stock-and-oversell.md)

## 맥락

주문 도메인을 처음 넣는다. 세 가지를 정해야 했다 — 주문이 가질 수 있는 상태의 범위,
남의 주문에 접근했을 때의 응답, 취소가 재고를 복원하는 방식.

[0011](0011-single-sellable-unit.md) 이 "옵션을 넣을지"의 재검토 시점을 주문 도메인
설계 직전으로 잡아 뒀다. 이번 범위(장바구니식 다중 라인, 상품은 여전히 단일 판매
단위)는 그 결정을 뒤집을 근거를 아직 주지 않아 그대로 둔다.

## 결정

**상태는 `PLACED` → `CANCELLED` 뿐이다.** 결제·배송 도메인이 없으므로 그 상태를
미리 만들지 않는다.

**본인 소유가 아닌 주문은 `404 ORDER_NOT_FOUND` 로 답한다.** `403` 을 따로 두지 않는다.
조회와 취소 둘 다 같다.

**취소도 재고 차감처럼 조건부 원자 갱신으로 막는다.** `OrderRepository.cancelIfPlaced(id)`
가 `WHERE status = 'PLACED'` 로 전이하고, 전이에 실제로 성공했을 때만 재고를 복원한다.

**재고 부족·판매중단 사유는 상품 도메인의 기존 예외를 재사용한다.** `ProductNotOnSaleException`,
`ProductDiscontinuedException` 은 그대로 쓰고, `InsufficientStockException` 만
`core.domain.product` 패키지에 새로 둔다 - 재고는 상품이 든 불변식이기 때문이다([0014](0014-stock-and-oversell.md)).

## 근거

**왜 403 이 아니라 404 인가**

주문 ID 는 상품 ID 와 마찬가지로 순차 발급되는 내부 PK 를 그대로 노출한다([0005](0005-uniqueness-and-email-enumeration.md)
가 회원 식별자에 유니크 제약이라는 다른 방어선을 둔 것과 대비된다). `403` 으로 답하면
"이 ID 의 주문은 존재하지만 내 것이 아니다"가 드러나, ID 를 순회하며 존재 여부와 발급
속도를 추정할 수 있게 된다. `TokenReissueService` 가 리프레시 토큰 해시로 소유자를
증명하게 한 것과 달리, 주문은 URL 경로에 ID 가 그대로 실리므로 "찾을 수 없음"으로
통일하는 것이 유일한 방어선이다.

**왜 취소도 조건부 원자 갱신이 필요한가**

`Order.cancel()` 의 상태 검사만 믿고 저장하면, 동시에 들어온 취소 요청 두 개가 같은
`PLACED` 상태를 읽고 둘 다 통과한다. 최종 저장 순서와 무관하게 재고 복원은 두 번
일어난다 - 재고가 1 줄었다가 취소로 3 이 되는 식이다. [0014](0014-stock-and-oversell.md)
가 차감에서 막은 것과 정확히 같은 모양의 경합이라 같은 도구로 막는다. 도메인 메서드
(`Order.cancel`)는 남겨 둔다 - `Product.canFulfill` 처럼 정확한 실패 사유를 위한
사전 판정이지, 그 자체가 방어선이 아니다.

**왜 결제 상태를 미리 만들지 않는가**

결제 연동이 없는 상태에서 `PAID` 상태를 두면, 그 값을 누가 언제 어떻게 바꾸는지에
대한 답 없이 컬럼만 존재하게 된다. 결제 도메인이 생기는 시점에 그 도메인이 실제로
필요로 하는 상태 전이 규칙(부분 결제, 결제 실패, 재시도)을 보고 정하는 편이, 지금
추측으로 만든 상태를 나중에 뜯어고치는 것보다 싸다.

## 결과

**얻는 것**

- 소유권 검사가 응답 코드 하나(404)로 일관돼, 클라이언트가 "존재하지만 권한 없음"과
  "존재하지 않음"을 구분해서 다뤄야 할 필요가 없다.
- 취소·차감 양쪽 모두 같은 모양의 조건부 원자 갱신이라, 재고 관련 경합을 다루는 방법이
  코드베이스 전체에서 하나로 통일된다.

**치르는 비용**

- 정당한 소유자가 남의 주문 ID 로 잘못 요청했을 때도 "권한 없음"이 아니라 "찾을 수
  없음"을 보게 돼, 클라이언트 쪽에서 오탈자 여부를 스스로 판단하기 더 어렵다.
- 결제·배송이 생기면 `OrderStatus` 에 상태가 늘고, 그 전이 규칙이 지금의 `cancel()`
  하나보다 복잡해진다. 지금 범위에서는 그 복잡도를 미리 대비하지 않는다.

## 재검토 시점

결제 또는 배송 도메인을 추가할 때 `OrderStatus` 를 확장한다. 관리자·판매자가 "남의"
주문을 봐야 하는 요구가 생기면(고객센터, 정산) 404 통일 규칙에 예외가 필요해지므로
그때 이 문서를 갱신한다.
