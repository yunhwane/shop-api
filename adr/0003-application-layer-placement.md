# 0003. 애플리케이션 유스케이스는 api 모듈에 둔다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0004](0004-infrastructure-adapter-modules.md)

## 맥락

회원가입 유스케이스는 여러 협력자를 조율한다 — 인증 레코드 조회와 소비, 중복 확인,
비밀번호 인코딩, 저장. 이 조율 코드가 놓일 자리가 기존 4개 모듈에는 없다.

제약이 하나 있다. `ModuleDependencyTest` 의 `core 는 Spring 에 의존하지 않는다` 규칙이
`com.example.shopapi.core..` 전체에 걸려 있어, **core 안에서는 `@Service` 도 `@Transactional`도
붙일 수 없다.**

선택지는 셋이었다.

1. `api` 모듈에 둔다.
2. `application` 모듈을 신설한다(`com.example.shopapi.application`, core 밖이라 Spring 사용 가능).
3. `core-domain` 에 순수 클래스로 두고 `api` 에서 수동으로 빈 등록한다.

## 결정

**`api` 모듈의 `api/user/application` 패키지**에 `@Service` + `@Transactional` 로 둔다.

## 근거

- 3안은 트랜잭션 경계가 붕 뜬다. `@Transactional` 을 못 붙이므로 `api` 쪽에 경계를 잡는
  래퍼가 따로 필요하고, 결국 클래스만 하나 늘면서 조율 로직은 두 곳으로 쪼개진다.
- 2안이 구조적으로는 가장 정직하지만, 지금 이 모듈의 내용물은 서비스 클래스 몇 개뿐이다.
  모듈 하나를 추가하는 값(`settings.gradle.kts`, `Packages.kt`, 계층 규칙, 빌드 스크립트)에
  비해 얻는 게 없다. **웹 어댑터와 유스케이스가 붙어 있어서 실제로 아픈 순간**이 오면
  그때 뽑아내는 편이 낫고, 그 리팩터링은 패키지 이동이라 비용이 크지 않다.
- 유스케이스가 `api` 에 있어도 도메인 규칙은 여전히 `core-domain` 에 있다.
  `api` 로 새는 것은 조율과 트랜잭션 경계뿐이다.

## 결과

**얻는 것**

- 모듈 추가 없이 진행한다. 아키텍처 테스트도 손댈 필요가 없다.
- 트랜잭션 경계가 유스케이스 클래스 하나에 명확히 잡힌다.

**치르는 비용**

- 유스케이스가 웹 실행 모듈에 묶인다. 배치나 다른 진입점에서 재사용하려면
  그 시점에 `application` 모듈로 추출해야 한다.
- `api` 모듈이 커진다. 패키지 규율(`user/application`, `user/dto`, `user/` 컨트롤러)로
  버틴다.

## 규율

- 컨트롤러는 DTO ↔ 도메인 변환과 HTTP 관심사만 다룬다. 분기 로직을 넣지 않는다.
- 유스케이스는 `core-domain` 의 포트에만 의존한다. JPA 타입이나 Spring Data 리포지토리를
  직접 알지 못한다(`api 는 영속성 구현체를 직접 참조하지 않는다` 규칙이 강제한다).
- **메일 발송은 트랜잭션 커밋 이후에, 그러나 요청 스레드에서 동기로 한다.**
  트랜잭션 안에서 보내면 롤백되어도 메일이 이미 나가 있고, 반대로 이벤트로 비동기 발송하면
  실패해도 사용자는 이미 성공 응답을 받은 뒤라 오지 않는 메일을 기다리게 된다.
  트랜잭션 프록시는 self-invocation 에서 동작하지 않으므로 저장과 발송을 다른 빈으로 나눈다.
  자세한 내용은 설계 문서 6.1 절.

## 재검토 시점

두 번째 진입점(배치, 관리자 API, 메시지 컨슈머)이 같은 유스케이스를 필요로 할 때
`application` 모듈로 추출한다.
