# 0015. 상품 목록은 커서 페이지네이션으로 낸다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0006](0006-api-response-contract.md), [0012](0012-money-representation.md), [0013](0013-product-category-as-enum.md)

## 맥락

상품 목록은 이 서비스에서 가장 자주 불릴 조회다. 페이지를 나누는 방식은 응답 계약에
그대로 드러나고, 한 번 클라이언트가 쓰기 시작하면 바꾸기 어렵다.

`?page=3&size=20` 형태의 offset 방식이 흔하고 구현이 쉽다. Spring Data 의 `Pageable`
을 그대로 쓰면 코드가 몇 줄로 끝난다.

## 결정

**커서 기반**으로 낸다.

```
GET /api/v1/products?category=&keyword=&sort=&cursor=&size=

{ "data": { "items": [ ... ], "nextCursor": "...", "hasNext": true } }
```

- 커서는 **불투명한 base64 문자열**이다. 안에는 `정렬 조건 + 정렬 키 값 + id` 가 들어간다.
- 정렬은 `LATEST`(기본) / `PRICE_ASC` / `PRICE_DESC`.
- **총 개수(`totalElements`)를 주지 않는다.**
- 포트 시그니처에 Spring 의 `Pageable` / `Page` 가 등장하지 않는다. `core-domain` 의
  순수 타입(`ProductSearchCriteria`, `ProductPage`)을 쓴다.

## 근거

**왜 offset 이 아닌가**

두 가지 문제가 있고, 두 번째가 결정적이다.

1. **뒤 페이지일수록 느려진다.** `OFFSET 10000` 은 DB 가 10000행을 읽고 버린 뒤 다음
   20행을 준다. 건너뛴 비용은 인덱스로도 사라지지 않는다.
2. **목록이 움직이면 항목이 중복되거나 사라진다.** 1페이지를 본 사이에 새 상품이 하나
   등록되면 전체가 한 칸씩 밀려서, 2페이지의 첫 항목이 1페이지의 마지막 항목과 같아진다.
   상품이 하나 삭제되면 반대로 한 건이 조용히 건너뛰어진다. 무한 스크롤에서는 사용자
   눈에 바로 보인다.

커서는 "이 값 다음부터"를 묻기 때문에 둘 다 없다. 시작 위치를 인덱스로 바로 찾고,
그 사이에 무엇이 추가되든 이미 본 항목이 다시 나오지 않는다.

**커서에 `id` 를 함께 담는 이유**

정렬 키만으로는 부족하다. 가격이 같은 상품이 여럿이면 `price > :lastPrice` 의 경계에서
동점 항목이 통째로 빠지거나 반복된다. `id` 를 최종 타이브레이커로 붙여 **전순서**를
만든다.

```sql
WHERE (price, id) > (:lastPrice, :lastId)   -- PRICE_ASC
```

**커서에 정렬 조건까지 담는 이유**

`sort=PRICE_ASC` 로 받은 커서를 `sort=LATEST` 와 함께 보내면 결과가 아무 의미가 없다.
커서 안의 값이 다른 컬럼 기준의 위치이기 때문이다. 서버가 커서에 담긴 정렬을 쓰고,
쿼리 파라미터와 어긋나면 `400` 으로 거절한다. **클라이언트의 실수를 조용히 이상한
결과로 갚지 않는다.**

**왜 불투명 문자열인가**

커서의 구조가 눈에 보이면 클라이언트가 그것을 조립하기 시작하고, 그 순간 내부 정렬 키가
공개 계약이 된다. 정렬을 하나 추가하려다 클라이언트를 깨뜨리게 된다.

**서명하지 않는다.** 담기는 값이 공개 카탈로그의 가격과 id 뿐이라 감출 것이 없다.
다만 이는 **위조한 커서로 임의 위치를 열 수 있다**는 뜻이므로 — base64 는 암호가
아니다 — 커서에 권한이나 필터 신뢰에 관한 정보를 절대 담지 않는다. 커서는 "어디부터"만
말하고, "무엇을 볼 수 있는가"는 매 요청 서버가 다시 판단한다.

**왜 총 개수를 주지 않는가**

`COUNT(*)` 는 조건에 맞는 행을 매 요청마다 전부 센다. 커서로 얻은 이점을 그 한 줄이
그대로 깎아먹는다. "1,234개의 상품" 표시가 요구사항이 되면 별도 엔드포인트나 근사치로
따로 다룬다. **목록을 넘기는 일과 개수를 세는 일은 비용이 다르므로 분리한다.**

**포트에 `Pageable` 을 쓰지 않는 이유**

`core-domain` 은 Spring 에 의존하지 않는다. 이것은 스타일 문제가 아니라 빌드 설정과
ArchUnit 이 강제하는 제약이고, `Pageable` 하나가 들어오면 도메인 전체가 Spring Data 에
묶인다. 게다가 `Pageable` 은 offset 개념(`pageNumber`)을 들고 있어 커서 방식과 의미가
맞지도 않는다.

## 결과

**얻는 것**

- 페이지가 뒤로 갈수록 느려지지 않는다. 어느 위치든 인덱스 탐색 한 번이다.
- 카탈로그가 갱신되는 중에도 항목이 중복되거나 빠지지 않는다.
- 정렬을 추가해도 클라이언트가 깨지지 않는다.

**치르는 비용**

- **임의 페이지로 점프할 수 없다.** "5페이지로 가기"가 불가능하다. 이 결정은
  **무한 스크롤 또는 '더 보기' UI 를 전제한다.**
- 전체 개수와 전체 페이지 수를 보여줄 수 없다.
- 커서를 만들고 읽는 코드가 필요하다. 정렬을 추가할 때마다 인코딩 대상이 늘어난다.
- 정렬 기준마다 복합 인덱스가 필요하다. 정렬을 무제한으로 늘릴 수 없다는 뜻이다.

## 함께 기록해 두는 한계

`keyword` 는 `LIKE '%...%'` 로 구현한다. **앞이 열린 패턴은 인덱스를 타지 못하므로
전체 스캔이다.** 카탈로그가 작은 동안만 유효하고, 검색이 실제 기능이 되는 시점에는
전문 검색(full-text index 또는 검색 엔진)으로 옮겨야 한다. 이 한계를 모른 채 상품이
늘면 목록 API 가 서서히 느려지고 원인이 페이지네이션으로 오인되기 쉽다.

## 재검토 시점

페이지 번호 UI 가 요구사항이 될 때. 그때는 커서를 버리는 것이 아니라 **개수 조회를
분리한 하이브리드**(첫 화면만 offset, 이후 커서)를 먼저 검토한다.
