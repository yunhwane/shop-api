# 0012. 금액은 원 단위 정수로 다루고 통화를 두지 않는다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0007](0007-reconstitution-vs-input-validation.md), [0011](0011-single-sellable-unit.md)

## 맥락

상품 가격을 무엇으로 표현할지 정해야 한다. 이 타입은 앞으로 장바구니 합계, 주문 금액,
할인, 정산에 그대로 번진다. 나중에 바꾸면 금액을 다루는 코드 전부와 스키마가 함께 바뀐다.

후보는 셋이었다 — `Double`, `BigDecimal`, 최소 단위 정수(`Long`).

## 결정

`Money` 값 객체를 만들고 내부는 **원 단위 `Long`** 으로 든다. 통화 코드를 두지 않는다.

- 범위: `0` 이상, `1_000_000_000`(10억 원) 이하
- 연산: 덧셈, 곱셈(수량), 비교. **나눗셈을 두지 않는다**
- `of(raw)` / `reconstitute(stored)` 두 팩토리를 갖는다([0007](0007-reconstitution-vs-input-validation.md))

DB 컬럼은 `bigint` 다.

## 근거

**왜 부동소수가 아닌가**

`0.1 + 0.2 != 0.3` 이다. 금액에 쓰면 항목이 쌓일수록 합계가 어긋나고, 어긋난 금액이
결제와 정산으로 나간다. 논쟁의 여지가 없다.

**왜 `BigDecimal` 이 아닌가**

정밀도 문제는 없지만 두 가지를 끌고 온다.

- **`equals` 가 소수 자릿수(scale)까지 비교한다.** `BigDecimal("1000")` 과
  `BigDecimal("1000.00")` 은 `equals` 가 `false` 다(`compareTo` 만 `0`). 값 객체의
  동등성이 값이 아니라 **표현 방식**에 흔들린다는 뜻이고, DB 왕복 한 번에 scale 이
  달라지면 같은 금액이 다른 값이 된다. 이런 버그는 테스트에서 잘 안 잡힌다.
- 원화는 소수점을 쓰지 않는다. 쓰지 않는 자릿수를 위해 컬럼 정의에 정밀도와 scale 을
  더하고, 반올림 모드를 매 연산마다 판단해야 한다.

**왜 통화를 두지 않는가**

통화는 컬럼 하나로 끝나지 않는다. 함께 오는 것은 환율, 통화별 최소 단위(원은 1,
달러는 0.01), 그리고 **통화가 다른 금액끼리의 연산을 금지하는 규칙**이다. 마지막 것이
비싸다 — 모든 덧셈과 비교가 통화 일치 검사를 지고 다니고, 불일치는 런타임 예외라
검사를 빠뜨린 자리는 테스트로만 찾을 수 있다.

단일 통화 서비스에 그 구조를 미리 넣으면 항상 참인 조건을 매번 확인하는 코드가 된다.

**왜 상한을 두는가**

`0` 을 하나 더 붙인 입력을 값 객체가 잡는다. `bigint` 는 훨씬 큰 값을 담을 수 있지만,
담을 수 있다는 것과 담아야 한다는 것은 다르다.

함정 하나 — **상한은 넓히기는 쉬워도 좁히기는 어렵다.** 이미 저장된 값이 새 상한을
넘으면 `reconstitute` 가 `CorruptedDataException` 을 던져 그 상품의 조회가 전부
`500` 이 된다([0007](0007-reconstitution-vs-input-validation.md)). 좁힐 때는 데이터
점검이 먼저다.

**왜 나눗셈을 두지 않는가**

할인율이나 n분할 정산에는 반올림 규칙이 필요하고, **그 규칙은 기술이 아니라 정책이다**
(버림인가 반올림인가, 1원 오차를 누가 갖는가). 규칙 없이 나눗셈만 열어 두면 호출하는
곳마다 다른 답을 내고, 합계가 원본과 1원씩 어긋난다. 할인을 도입할 때 정책과 함께 넣는다.

**0원을 허용하는 이유**

사은품과 증정 상품이 실재한다. 0원 상품이 결제 흐름에서 곤란하다면 그것은 결제의
관심사이지 금액 타입의 관심사가 아니다.

## 결과

**얻는 것**

- 금액 연산에 오차가 없다. 합계는 정수 덧셈이다.
- 정렬과 비교가 DB 인덱스에서 그대로 동작한다([0015](0015-product-list-pagination.md)).
- `Money` 를 쓰는 자리에 `Long` 을 잘못 넣을 수 없다.

**치르는 비용**

- **해외 통화나 소수 단위 통화를 지금은 담을 수 없다.** 넣는 순간 `Money` 의 내부 단위가
  "원"이 아니라 "해당 통화의 최소 단위"로 바뀌고, 저장된 값의 해석도 통화에 의존하게 된다.
- 화면 표기(천 단위 구분, 통화 기호)는 표현 계층의 몫이다. `Money` 는 숫자만 안다.

## 재검토 시점

해외 통화 결제가 요구사항이 될 때. 그때 `Money` 에 통화를 더하고 내부 단위를 최소 단위로
재정의한다. **기존 행은 전부 KRW 로 채우는 마이그레이션 한 번으로 끝난다** — 지금 값이
이미 최소 단위 정수라서 값 자체는 바꿀 필요가 없다.
