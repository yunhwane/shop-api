# 0007. 저장된 값의 복원을 입력 검증과 분리한다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0006](0006-api-response-contract.md)

## 맥락

값 객체가 형식 검증을 맡고 있다(`Email.of`, `UserId.of`). 그런데 JPA 엔티티의
`toDomain()` 도 같은 팩토리를 썼다. **요청에서 온 값과 DB 에서 읽은 값이 같은 문을
통과한 것이다.**

두 경로는 실패했을 때 의미가 전혀 다르다.

- 요청 값이 규칙을 어긴다 → 클라이언트가 고칠 수 있다. `400`.
- 저장된 값이 규칙을 어긴다 → 클라이언트는 아무것도 할 수 없다. 서버나 데이터의 문제다.

같은 예외를 쓰면 후자가 `400 INVALID_REQUEST` 로 나간다. 실제 결과는 이렇다.
회원 조회에서 깨진 행을 만나면 응답이 `errors[0].field = "email"` 을 담는데,
**가입 요청은 `email` 을 받지도 않는다**([0002](0002-email-verification-token-design.md)).
클라이언트는 보낸 적 없는 필드를 고치라는 말을 듣는다. 게다가 4xx 는 `warn` 으로 남아
에러 로그에 걸리지 않으므로, 고쳐야 할 사람이 그 행의 존재조차 모른다.

지금은 H2 `create-drop` 에 쓰기 경로가 하나뿐이라 이런 행이 생길 수 없다. 실 DB 와
마이그레이션, 수동 데이터 주입이 들어오면 생긴다.

## 결정

값 객체에 팩토리를 둘 둔다.

| | 용도 | 실패 시 |
|---|---|---|
| `of(raw)` | 바깥에서 들어온 입력 | `InvalidValueException` → `400 INVALID_REQUEST` |
| `reconstitute(stored)` | 저장소에서 읽은 값 | `CorruptedDataException` → `500 INTERNAL_ERROR` |

`reconstitute` 는 **검증을 건너뛰지 않는다.** `of` 를 그대로 호출하고 실패의 종류만
바꾼다. 호출 위치는 ArchUnit 이 `storage` 모듈로 제한한다.

## 근거

**왜 검증을 건너뛰지 않는가**

건너뛰는 편이 빠르고, 저장된 값은 이미 `of` 를 통과했으니 안전하다고 볼 수도 있다.
하지만 그 전제가 깨지는 경우가 정확히 이 결정이 다루려는 상황이다 — 마이그레이션,
손으로 넣은 행, 나중에 규칙을 좁힌 경우. 검증을 끄면 규칙을 어기는 값이 도메인 안으로
조용히 흘러들고, **값 객체가 보장한다고 말하는 불변식이 거짓이 된다.** 그때 터지는
곳은 훨씬 먼 지점이라 원인을 찾기 어렵다. 읽기 한 건당 정규식 하나가 그 대가로 싸다.

**왜 500 인가**

클라이언트가 할 수 있는 일이 없다. 재시도해도 같은 행을 읽고 같은 결과가 나온다.
5xx 로 내보내면 `GlobalExceptionHandler` 가 `error` 로 로그를 남기고 모니터링에 잡힌다.

**왜 호출 위치를 규칙으로 막는가**

이름만으로는 오용을 막지 못한다. `reconstitute` 를 입력 경로에서 쓰면 클라이언트가 보낸
잘못된 값이 400 대신 500 으로 나가면서 사용자는 무엇을 고칠지 알 수 없게 되고,
서버는 자기 잘못이 아닌 것으로 에러 알림을 받는다. 방향만 반대일 뿐 같은 종류의 사고다.

## 결과

**얻는 것**

- 서버 데이터 문제가 4xx 계약을 오염시키지 않는다.
- 깨진 행이 에러 로그에 남는다.
- 값 객체의 불변식이 읽기 경로에서도 유지된다.

**치르는 비용**

- 값 객체마다 팩토리가 하나씩 늘어난다. 새 값 객체를 만들 때 둘 다 필요한지 판단해야 한다.
  저장되지 않는 값(`RawPassword`)에는 `reconstitute` 를 두지 않는다.
- 읽기마다 검증이 한 번 더 돈다. 대량 조회가 문제가 되면 그때 다시 본다.
- `CorruptedDataException` 의 메시지에는 필드 이름만 담는다. 값에 해시나 토큰이 섞일 수 있어
  디버깅 정보가 줄어드는 대신, 로그로 비밀이 새지 않는다.

## 재검토 시점

읽기 경로가 성능 문제가 되거나, 스키마 검증을 DB 제약으로 옮겨 애플리케이션 검증이
중복이 되는 시점.
