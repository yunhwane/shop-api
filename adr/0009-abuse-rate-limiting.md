# 0009. 남용 방지 호출 제한은 인메모리 고정 창으로 시작한다

- 상태: 수락됨
- 날짜: 2026-09-01
- 관련: [0005](0005-uniqueness-and-email-enumeration.md), [0008](0008-login-token-strategy.md)

## 맥락

[0005](0005-uniqueness-and-email-enumeration.md) 에서 가입된 이메일의 존재를 `409` 로
노출하기로 하면서, 완화책으로 "열거 자체를 비싸게 만든다"를 후속 작업에 남겼다.
그것이 아직 없어서 **지금은 이메일 열거가 무료다.**

막아야 할 남용은 셋이고 서로 다른 열쇠를 요구한다.

| 남용 | 형태 | 막는 열쇠 |
|---|---|---|
| 이메일 열거 | 한 곳에서 **여러 주소**를 시도 | 발신 IP |
| 메일 폭탄 | **한 주소**로 발송을 반복 요청 | 대상 이메일 |
| 자격 대입 | 한 곳에서 여러 아이디·비밀번호 | 발신 IP |

## 결정

**인메모리 고정 창(fixed window) 카운터**를 `RateLimiter` 포트 뒤에 둔다.

| 엔드포인트 | 열쇠 | 기본값 |
|---|---|---|
| `POST /email-verifications` | IP | 10회 / 1시간 |
| `POST /email-verifications` | 이메일 | 3회 / 1시간 |
| `POST /auth/login` | IP | 20회 / 5분, **실패만 센다** |

초과하면 `429 TOO_MANY_REQUESTS` 와 `Retry-After` 헤더를 준다.

## 근거

**왜 로그인은 아이디 단위로 막지 않는가**

막고 싶어지지만 그러면 **공격자가 남의 계정을 잠글 수 있다.** 아무 아이디로 틀린
비밀번호를 한도만큼 보내면 진짜 주인이 그 창 동안 못 들어온다. 보호하려던 계정을
공격 도구로 만드는 셈이다. IP 단위만 두고, 아이디 단위 보호는 나중에
점증 지연이나 CAPTCHA 처럼 잠금이 아닌 수단으로 다룬다.

**왜 로그인은 실패만 세는가**

정상 사용자의 성공한 로그인이 한도를 깎을 이유가 없다. 사무실이나 학교처럼 여러
사람이 한 IP 를 쓰는 환경에서, 성공까지 세면 아무도 공격하지 않았는데 한도가 찬다.

**왜 이메일 단위 제한은 두는가**

이쪽은 잠금 부작용이 가볍다. 막히는 사람은 **아직 회원이 아니고**, 한 시간 뒤
다시 시도하면 된다. 반대로 없으면 아무나 남의 주소로 메일을 무한정 보낼 수 있고,
그 비용은 우리가 Resend 에 낸다.

**왜 라이브러리를 쓰지 않는가**

Bucket4j 같은 선택지가 있지만 Spring Boot BOM 이 관리하지 않아 버전을 직접
들어야 한다. 지금 필요한 것은 카운터 하나이고, 포트 뒤에 있으므로 나중에 교체가
어댑터 교체로 끝난다.

## 결과

**얻는 것**

- 열거와 메일 폭탄이 더 이상 무료가 아니다.
- 제한 방식 교체가 어댑터 하나로 끝난다.

**치르는 비용 — 이 구현의 한계를 분명히 해 둔다**

- **인스턴스마다 카운터가 따로다.** 서버를 늘리면 실질 한도가 대수만큼 곱해진다.
  여러 대로 가는 순간 Redis 같은 공유 저장소로 옮겨야 한다.
- **재시작하면 카운터가 초기화된다.** 배포로 제한이 풀린다.
- **고정 창은 경계에서 두 배까지 통과시킨다.** 창이 바뀌는 순간에 몰아치면
  한도의 두 배가 지나간다. 열거를 느리게 만드는 목적에는 충분하다고 보고 감수한다.
- **IP 는 신뢰할 수 없는 값이다.** 프록시 뒤에 두면 `X-Forwarded-For` 를 봐야 하는데,
  그 헤더는 클라이언트가 지어낼 수 있다. **신뢰할 수 있는 프록시를 앞에 두고
  그 설정을 맞추기 전까지 IP 기반 제한은 우회 가능하다.** 지금은 프록시가 없어
  원격 주소를 그대로 쓴다.

## 재검토 시점

인스턴스를 둘 이상으로 늘릴 때. 그때는 선택이 아니라 필수다.
