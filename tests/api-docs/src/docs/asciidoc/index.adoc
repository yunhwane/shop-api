[[overview]]
== 개요

이 문서는 테스트가 실제로 보낸 요청과 받은 응답으로 만들어진다. 구현이 바뀌면
문서를 만드는 테스트가 먼저 깨지므로, 여기 적힌 내용과 동작이 어긋난 채로 배포될 수 없다.

[[overview-response]]
=== 응답 형식

성공과 실패의 형식이 다르다.

[cols="1,2,3"]
|===
| | Content-Type | 형태

| 성공 (2xx)
| `application/json`
| `data` 한 겹으로 감싼 봉투

| 실패 (4xx/5xx)
| `application/problem+json`
| https://www.rfc-editor.org/rfc/rfc9457[RFC 9457] ProblemDetail
|===

실패 응답을 봉투에 넣지 않는 이유는 ProblemDetail 의 값이 표준이라는 점에 있기 때문이다.
자체 봉투로 감싸면 클라이언트 라이브러리와 게이트웨이가 그것을 표준으로 인식하지 못한다.

[[overview-errors]]
=== 에러 코드

HTTP 상태만으로는 구분되지 않는 경우가 있다. `409` 하나에 세 가지가 들어간다.
클라이언트는 상태 코드가 아니라 확장 필드 `code` 로 분기한다.

[cols="2,1,4"]
|===
| code | status | 언제

| `INVALID_REQUEST` | 400 | 요청 형식이나 값이 규칙을 어겼다. `errors` 에 필드별 사유가 담긴다
| `VERIFICATION_NOT_COMPLETED` | 400 | 이메일 인증을 마치지 않고 가입을 시도했다
| `VERIFICATION_EXPIRED` | 400 | 인증 기한이 지났다
| `INVALID_VERIFICATION_TOKEN` | 400 | 메일 링크의 토큰으로 아무것도 찾지 못했다
| `VERIFICATION_NOT_FOUND` | 404 | `verificationId` 로 인증을 찾지 못했다
| `PRODUCT_NOT_FOUND` | 404 | 상품이 없거나, 아직 공개되지 않았거나, 단종됐다
| `DUPLICATE_USER_ID` | 409 | 이미 쓰이는 아이디다
| `DUPLICATE_EMAIL` | 409 | 이미 가입된 이메일이다
| `VERIFICATION_ALREADY_USED` | 409 | 이미 가입에 사용된 인증이다
| `INVALID_CREDENTIALS` | 401 | 아이디가 없거나 비밀번호가 틀렸다. 둘을 구분하지 않는다
| `INVALID_REFRESH_TOKEN` | 401 | 리프레시 토큰이 없거나 기한이 지났다
| `REFRESH_TOKEN_REUSED` | 401 | 이미 쓴 리프레시 토큰이 다시 왔다. 모든 기기에서 로그아웃된다
| `UNAUTHENTICATED` | 401 | 액세스 토큰이 없거나 유효하지 않다
| `ACCOUNT_SUSPENDED` | 403 | 정지된 계정이다
| `ACCOUNT_WITHDRAWN` | 403 | 탈퇴한 계정이다
| `ACCESS_DENIED` | 403 | 권한이 없다
| `MAIL_SEND_FAILED` | 502 | 메일 게이트웨이 호출이 실패했다
| `INTERNAL_ERROR` | 500 | 그 외
|===

[[sign-up]]
== 회원가입

이메일 인증을 **가입보다 먼저** 수행한다. 인증에 성공한 요청만 가입을 받으므로,
회원 레코드가 존재한다는 것은 이메일 소유가 확인됐다는 뜻이다.

식별자가 둘이라는 점에 주의한다.

* `verificationId` — 발송 요청의 응답으로 클라이언트가 받아 보관한다. 비밀이 아니다.
* `token` — 메일 링크에만 담긴다. 응답 본문에 절대 나오지 않는다.

가입에는 둘 다 필요하다. 토큰만 가로챈 제3자는 `verificationId` 가 없어 가입하지 못하고,
`verificationId` 만 가진 클라이언트는 메일함 없이 인증을 통과하지 못한다.

[[sign-up-request-verification]]
=== 인증 메일 발송 요청

이미 가입된 이메일이면 `409 DUPLICATE_EMAIL` 로 응답한다. 같은 주소로 다시 요청하면
아직 누르지 않은 이전 링크는 무효가 되지만, **이미 인증을 마친 건은 그대로 유지된다.**

operation::email-verification-request[snippets='http-request,request-fields,http-response,response-fields']

[[sign-up-confirm]]
=== 인증 완료

메일의 링크는 이 API 를 직접 가리키지 않는다. 프론트엔드의 `/verify?token=...` 페이지를
가리키고, 그 페이지가 이 API 를 호출한다. 메일 클라이언트가 링크를 미리 가져가면서
사용자 대신 인증을 눌러 버리는 것을 막기 위해서다.

이미 인증된 건에 대해서는 멱등하게 성공한다. 링크를 두 번 눌러도 실패하지 않는다.

[[sign-up-create-user]]
=== 가입

**요청 본문에 `email` 이 없다.** 이메일은 서버가 `verificationId` 로 조회한 인증
레코드에서 가져온다. 바디로 받으면 A 를 인증하고 B 로 가입하는 경로가 열린다.

인증은 가입에 쓰이는 순간 소비된다. 같은 `verificationId` 로 두 번 가입할 수 없다.

operation::user-sign-up[snippets='http-request,request-fields,http-response,response-fields']

[[products]]
== 상품 카탈로그

인증이 필요 없다. 상품 등록과 수정은 **이 API 에 없다** — 권한 모델이 정해지기 전까지
쓰기 엔드포인트를 열지 않는다.

`availability` 는 저장된 값이 아니라 판매 상태와 재고에서 파생된다. 재고가 0 이 되는
순간 별도의 갱신 없이 `SOLD_OUT` 이 된다.

[[products-list]]
=== 상품 목록

페이지 번호가 아니라 **커서**로 넘긴다. 응답의 `nextCursor` 를 그대로 다음 요청에
실어 보내면 된다.

[IMPORTANT]
====
**커서와 `sort` 를 함께 바꿀 수 없다.** 커서 안에는 그 정렬 기준에서의 위치가 들어 있어,
다른 정렬로 이어 붙이면 결과가 의미를 잃는다. 어긋나면 `400` 으로 거절한다.
정렬을 바꾸려면 커서 없이 첫 쪽부터 다시 요청한다.
====

총 개수를 주지 않는다. 조건에 맞는 행을 매 요청마다 전부 세면 커서로 얻은 이점을
그대로 깎아먹기 때문이다. `hasNext` 로 마지막 쪽인지 판단한다.

`keyword` 는 상품명 부분 일치다. `%` 와 `_` 는 와일드카드가 아니라 글자 그대로 찾는다.

operation::product-list[snippets='http-request,query-parameters,http-response,response-fields']

[[products-detail]]
=== 상품 상세

**판매를 일시 중지한 상품도 열린다.** `availability` 가 `UNAVAILABLE` 로 나갈 뿐이다.
이미 링크를 가진 사람에게 `404` 를 주면 "일시적으로 판매하지 않는다"가 "없어졌다"로 읽힌다.

공개 전(`DRAFT`)이거나 단종된 상품은 존재하지 않는 것과 같은 `404` 로 답한다.
구분해서 알려주면 아직 공개하지 않은 상품의 존재가 드러난다.

operation::product-detail[snippets='http-request,path-parameters,http-response,response-fields']

[[auth]]
== 로그인

액세스 토큰은 30분짜리 JWT 이고, 리프레시 토큰은 14일짜리 불투명 난수다.
인증이 필요한 요청에는 `Authorization: Bearer {accessToken}` 을 붙인다.

[IMPORTANT]
====
**재발급할 때마다 리프레시 토큰이 바뀐다.** 응답의 새 값을 반드시 저장해야 한다.

옛 값을 다시 보내면 유출로 간주해 그 사용자의 모든 리프레시 토큰이 폐기되고,
정상 사용자까지 다시 로그인해야 한다. 회전만으로는 탈취를 막지 못하기 때문에
둔 장치다 — 탈취범이 먼저 재발급을 받아 가면, 정상 사용자가 이미 소비된 토큰을
들고 오게 되고 그 사실 자체가 유출의 신호다.
====

[[auth-login]]
=== 로그인

아이디가 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는다. 요청 형식이 규칙을
어겨도 `400` 이 아니라 같은 `401` 로 응답한다 — 상태 코드 차이만으로 아이디 규칙과
존재 여부를 좁혀 갈 수 있기 때문이다.

정지된 계정은 다르다. **비밀번호가 맞은 뒤에** `403 ACCOUNT_SUSPENDED` 로 알린다.
